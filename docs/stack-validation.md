# Fiji ROI 연동과 실제 XRT 스택 검증 (Issue #39)

## 검증 환경

2026-10-04, Windows의 `C:\Users\PC-1\OneDrive\Desktop\캡스톤 디자인\3D XRT`에서 실제 TIFF 4개를 읽었습니다. Linux 원래 경로 대신 이 환경에 존재하는 파일을 사용했습니다. Python 3.13, PySide6 6.11.2, Java 24, 고정된 Fiji 라이브러리로 실행했습니다.

기존 원본 페이지 검증 도구와 신규 QML 검증 도구를 실행했습니다. 신규 도구는 실제 Main.qml과 FileBridge를 로드하되 **Qt offscreen** 환경에서 자동 조작합니다. 네이티브 파일 선택 창의 마우스 조작, GPU FPS 또는 사람이 눈으로 확인한 화면 품질을 측정한 결과는 아닙니다. 실제 이미지나 처리 결과·픽셀 값·스크린샷은 Git에 넣지 않습니다.

**4개 모두 PASS**:

- 첫·중간·마지막 페이지의 원본 배열을 독립 tifffile 읽기와 전체 비교했습니다. ImageJ 초기 표시 범위를 사용하고, 범위 변경 시 표시가 바뀌어도 원본 배열은 같았습니다.
- 준비 완료 후 전 페이지 정방향/역방향 요청 총 **1,252회**가 즉시 해당 페이지를 표시했습니다. 시간은 GUI 이벤트에서 요청/상태 발행까지의 CPU 시간이며 실제 디스플레이 프레임률이 아닙니다.
- 화면 맞춤 크기와 100%·200%·400%로 두 위치를 확대·이동했습니다. 원본 배율 이상에서 중심 표시 픽셀이 원본 값의 표시 변환과 정확히 일치했습니다. 800×600 CPU 페인팅의 최댓값은 파일별 2.29–3.80 ms였습니다.
- 검사한 12개 페이지 각각에서 실제 Fiji `MultiplyDataValuesBy`로 32×32 사각형 ROI 값을 절반으로 처리했습니다. ROI 밖 전체 픽셀과 ROI 안의 Fiji 반올림 결과를 비교했습니다. 내부 작업 파일만 생성했고 원본 파일 크기와 수정 시각은 모두 유지되었습니다.
- 같은 파일 다시 열기와 닫기 후 이전 표시 계층의 mmap 및 임시 디렉터리가 정리되는 것을 확인했습니다. 마지막으로 QML 경고가 없는지도 확인했습니다.
- 읽기 동안 10ms Qt 타이머가 계속 실행됐습니다. 파일별 최대 간격은 32–185ms였으며 완전히 무응답 상태로 읽지는 않았습니다. 이 수치를 모든 하드웨어의 응답 시간 보장으로 해석하지 않습니다.

## 메모리와 남은 제약

- 탐색 캐시는 약 **401–465 MiB**, raw 캐시는 **46–53 MiB**였습니다. 디스크 표시 계층은 파일별 약 **826 MiB–3.62 GiB**였습니다. 매핑 가능한 TIFF는 원본을 읽기 전용으로 매핑하고, 비매핑 TIFF는 페이지별 임시 파일을 사용합니다.
- 준비 완료 시 뷰어 프로세스 working set은 약 **3.72–4.28 GiB**, 검사 전체 최고 기록은 **4.45 GiB**였습니다. 매핑된 원본과 표시 파일의 실제 resident 페이지도 포함하므로 캐시 배열 크기나 Python 힙 크기와 같지 않습니다. 별도 JVM 프로세스 메모리는 이 숫자에 포함되지 않습니다.
- 닫은 뒤 뷰어 working set은 **242–252 MiB**로 내려갔습니다. 탐색 캐시 한도가 프로세스 전체 RAM 한도는 아닙니다. 메모리가 작은 PC를 위한 디스크 캐시 정책·매핑 페이지 상주량 개선은 후속 작업입니다.
- Fiji 전체 스택의 편집용 Dataset은 **512 MiB까지**이므로 이 4개 파일은 **현재 페이지 처리**를 사용합니다. 작은 합성 스택에서만 현재 페이지/모든 페이지 ROI 처리를 추가 검사했습니다.
- 모든 Fiji 명령이 ROI를 적용하는 것은 아닙니다. Overlay/ImageDisplay 선택을 사용하는 명령만 연동하며 Dataset만 처리하는 명령은 전체 이미지를 바꿀 수 있습니다. ROI Manager 양방향 동기화, 프로젝트 영구 저장, 3D 재구성과 모델 분석은 후속 단계입니다.
